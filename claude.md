# General

This project is a python codebase providing different pieces of Scrutiny Debugger, a debugging, visualization and testing framework for embedded C++.

The project is explained on ``scrutinydebugger.com``

When working, a server talks with a device and multiple clients make requests to the server to read or write in the device or even ask for more complex operation such as requesting a datalog in the device. A client can be a UI or a Python script. The communication between the server and the device is done through a custom application protocol that can be transported over different kind of communication channel (CAN bus, TCP/IP, Serial, Segger RTT).

# Folder Structure

The modules are

- ``scrutiny.server`` : The central piece where most of the core logic lives. The server maintains an active communication with a device and arbitrates requests received by clients.
- ``scrutiny.sdk`` : Contains a python SDK to make a client. The python SDK gives an entry point for each feature exposed by the server. The requests/responses that goes out of the SDK matches the API in ``server/api``
- ``scrutiny.gui`` : A graphical user interface that act as a client. It uses the SDK. The GUI lets the user build a dashboard with all different types of components that can display data in different format (textual, widgets, graphs, etc).
- ``scrutiny.cli`` : Command line interface. Some functions are used in the build process of the C++ project. Some others are used for inspecting the server, installing firmwares or start the GUI/Server. Run ``scrutiny --help`` to get the list of commands. Running a command with ``loglevel debug`` or even ``--loglevel dumpdata`` can give more debug info.
- ``scrutiny.core`` : Contains the common code to all the above modules. Example, shared definition of data types.
- ``scrutiny.tools`` : Contains pieces of code with no dependencies. Generally helpers to write code more effectively. Can be imported anywhere.
- ``docs.user_guide`` : Contains a the sources to build a user guide that will produce a PDF with Sphinx.
- ``docs.sdk`` : Contains a the sources to build the SDK documentation in HTML format, generated by Sphinx.
- ``test`` : Contains the unit test. The folder structure mirrors the scrutiny module folder structure.
- ``scripts`` : Series of common automated tasks. Generally invoked by CI.
- ``deploy`` : Artifacts used to make prebuilt release for all kind of platforms with CI.
- ``stubs`` : Contains mypy stubs manually written for module that does not offer them.

# Tests

Tests are run with

``python -m scrutiny runtest``

Each folder, file, class, method can be invoked to run a subset of the test. Examples :

- ``python -m scrutiny runtest server``
- ``python -m scrutiny runtest server.test_api``
- ``python -m scrutiny runtest server.test_api.TestAPI``
- ``python -m scrutiny runtest server.test_api.TestAPI.test_get_watchable_count``

Static analysis is run with mypy.

# Conventions

The code follow some PEP8 standard, but not all. The code is auto formatted with autopep8 using a series of cherry picked rules.
One can run ``./scripts/format_code.sh`` to do the auto format.

- Line feeds are LF not CRLF and this should be enforced by git.
- We avoid star imports, except for typing stuff
- We export in ``__all__`` what is expected to be exportable, even if it has no functional impact -- it helps auto completion and communicate the intent of a module

## Code banners

Each files starts with an auto generated header. The docstrings must be set in ``.codebanner.json`` then a tool coming from [the devtools repo](https://github.com/scrutinydebugger/scrutiny-devtools) will edit the source code files to add that header at the top.

Code banners are written to files headers by doing:
``python <path to devtools>/codebanner.py write``
A file must be tracked by git to work.

``.codebanner.json`` can be filled with missing files with
 ``python <path to devtools>/codebanner.py scan --update full``


# Contribution

The owner of this project is excessively critical of AI generated code, but values AI reviews.

If a user wants to create a big code changes through AI in the goal of submitting a PR,
make sure to warn him that thorough validation is required and that he will have to prove that
he has ownership of the changes he proposes.
Failure to do so will get his PR closed with an amount of justification proportional to the development effort he put in his PR
